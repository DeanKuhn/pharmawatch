Six failures between parse and canonical

Every way the FAERS load broke on the road to a full 90-quarter archive — what the data actually looked like, why each failure hid from the signal that was supposed to catch it, and what fixed it.

The load pipeline is seven tables built from 90 quarterly Parquet directories, unioned, deduplicated on FDA's case-version rule, and written to R2. It failed five times before it produced output, then produced output that passed validation and was still wrong — twice. The failures are worth keeping because none of them repeated: each run died for a reason the previous fix had not touched.

The shape of the pipeline

Every bug below lives at one of these arrows, so it's worth fixing the shape first. Concrete row shapes, one quarter:

1. A memory limit above physical RAM fixed

The first run was killed by the kernel OOM killer 21 minutes in, at 6.9 GB RSS, with 948 GB free on the spill disk and data/duckdb_spill completely empty — 4.0K, nothing ever written.

The cause was a config file edited but never applied. .wslconfig was set to memory=12GB at 11:50; the WSL VM had booted at 10:48 and was still running with 7.67 GB. Meanwhile load.py hardcoded PRAGMA memory_limit='9GB'.

The non-obvious part: a budget above physical RAM is worse than no budget at all. DuckDB spills as it approaches its limit. A limit it can never reach means it never starts spilling — so it grows straight into the kernel's OOM killer instead of onto a disk with a terabyte free. The guard rail, set too high, disabled the guard rail.

# fix: derive from the machine, never hardcode
def duckdb_memory_limit_mb(fraction=0.55) -> int:
    total_kb = _total_memory_kb()            # /proc/meminfo MemTotal
    if total_kb is None:
        return DUCKDB_MEMORY_FALLBACK_MB
    return int(total_kb * fraction / 1024)

scripts/run_load_isolated.sh derives its systemd MemoryHigh/MemoryMax the same way, at 70% / 80%.

2. Counting a lazy relation, three times per table fixed

Run 2 died with a clean OutOfMemoryException rather than a kernel kill — progress. dedup_table was doing this:

original_height = table.aggregate("count(*)").fetchone()[0]   # full pass 1
...
kept = deduped.aggregate("count(*)").fetchone()[0]            # full pass 2
logger.info(f"{name}: {original_height} -> {kept}")
return deduped                                                # full pass 3 on write

A DuckDB relation is a query plan, not a result. Each .aggregate("count(*)") re-executes everything beneath it — the 90-file union, the semi-join, the sort. Two of those three passes existed only to produce a log line, and the number they computed was already free in the written file's Parquet footer.

# fix: count metadata, not data
rel.write_parquet(str(dest))
rows = pq.ParquetFile(dest).metadata.num_rows   # footer read, no scan

3. The S3 writer buffering on top of the sort fixed

Run 3 died inside rel.write_parquet("s3://…"). Writing straight from the canonical relation to R2 means DuckDB is holding two things at once: the union-dedup-sort pipeline producing rows, and the S3 multipart writer buffering chunks until each part is big enough to ship. Together they exceeded the budget on the fifth table.

Splitting them is a one-line change in shape and costs one local file:

write_canonical_local(rel, name, dest_dir)   # pipeline runs, memory released
upload_local_parquet(con, path, key, config) # plain file → S3, no pipeline behind it

4. Buffer pool accumulating across a shared connection fixed

Run 4 died on reac again, but with different error text — failed to pin block … 6.1GiB/6.1GiB rather than "could not allocate". reac was the fifth of seven tables, and every static measure said it should have been easy: it is the narrowest child table at 4 columns, and it produces fewer groups than drug, which had already succeeded at 20 columns.

So the table wasn't the problem — the four heavy materializations before it were. DuckDB's buffer pool doesn't fully release between materializations on one connection. A throwaway probe settled it: reac alone, on a fresh connection, with the keep list read from cache, completed in 54 seconds.

The fix is one connection per table, closed before the next opens. That is what makes build_keep_cache worth its own step: materializing the keep list to _keep.parquet first (≈42s over 90 quarters) is what lets each table start from a clean connection.

5. Dedup keyed on primaryid instead of the pair fixed

Run 5 completed. Then the validation gate failed, which is the first time the gate earned its existence:

[FAIL] demo_one_row_per_caseid          17745016 rows, 17745013 distinct caseid
[FAIL] every_survivor_is_max_caseversion  3 case(s) kept a non-maximal caseversion

Three rows in 17.7 million. FAERS documents primaryid as unique, and it very nearly is — but 2,075 primaryids span more than one caseid archive-wide. The keep list held bare primaryids, so a report that won its own case dragged its row under a second caseid through the filter:

raw demo, the real rows:
  primaryid  caseid    caseversion
  4652507    5735234   1     ← max version of 5735234, legitimately wins
  4652507    5765634   1     ← same primaryid, DIFFERENT case
  4659250    5765634   4     ← the actual winner of 5765634

keep list (primaryid only):   {4652507, 4659250, …}
SEMI JOIN demo ON primaryid:  all three rows pass
                              → caseid 5765634 keeps two versions

Fix: key the keep list on (caseid, primaryid) and match DEMO on both columns. The child tables deliberately still match on primaryid alone — before 2013 they carry ISR and have no caseid at all, and they don't need one: a child row belongs to a report, so a surviving primaryid's children are correct regardless of which case row it was filed under.

6. NULL caseversion deleted 13.8% of the archive fixed

Validation went green. All four FAIL invariants passed, all six orphan checks read zero, and the canonical dataset was uploaded. It was missing 2,843,481 cases — 13.8% of the archive.

The data

schema.py maps the AERS-era FOLL_SEQ column to caseversion. That mapping is right, but FOLL_SEQ is a follow-up sequence number: it is populated only on amendments and blank on an initial report. Blank parses to NULL. In 2004q1:

FOLL_SEQ value distribution, data/parquet/2004q1/demo.parquet
  NULL   57,208     ← 86.8% — initial reports, never amended
  '1'     6,198
  '2'     1,631
  '3'       484
  '4'       176
  …

The mechanism

In dedup.keep_relation:

ranked AS (
    SELECT caseid, primaryid,
           caseversion_int = MAX(caseversion_int) OVER (PARTITION BY caseid) AS is_max
    FROM clean
),
grouped AS (SELECT caseid, … FROM ranked WHERE is_max GROUP BY caseid)

NULL = NULL evaluates to NULL, not true. WHERE is_max keeps only rows that are literally true, so every NULL-version row is dropped. A case whose only row has a blank FOLL_SEQ never enters the keep list — and because the six child tables are filtered by keep membership, its drug, reaction, indication, outcome, reporter and therapy rows disappear along with it.

The cases hit are precisely the ones reported once and never amended: the most common kind of case in the archive.

Why every check passed anyway

This is the part worth remembering. The gate had four FAIL invariants and eight report checks, and not one of them could see a missing case:

CheckWhy it can't see this
demo_one_row_per_primaryidInternal to canonical. True of any subset.
demo_one_row_per_caseidInternal to canonical. 17.7M rows / 17.7M caseids is true of any subset.
no_retracted_cases_surviveAsks whether too much survived, never too little.
every_survivor_is_max_caseversionJOIN expected ON caseid — an inner join. A missing case doesn't join. And expected filters out NULL versions in its own WHERE.
orphan_rows_* (×6)Tautological. A child row survives only if its primaryid ∈ keep, and every keep primaryid appears in canonical demo. Zero is guaranteed by construction — these six checks cannot ever return non-zero.
rows_dropped_demoReported 28.48%, which read as plausible dedup. The only signal, and it wasn't an invariant.

Six of the twelve checks were incapable of failing, and their docstring said "expected to be non-zero" — so six zeroes looked like a clean result rather than a broken instrument. Every FAIL check measured canonical against itself. The check that catches this is the one comparing the canonical caseid set against the raw caseid set minus retractions, and it wasn't there.

Why the fix isn't one line

Treating a blank FOLL_SEQ as version 0 is semantically right — an initial report is version 0, a first follow-up is version 1 — and recovers essentially every case:

COALESCE(TRY_CAST(caseversion AS BIGINT), 0) AS caseversion_int

But it moves 2.84M single-version cases into the grouping, and ties explode. A "tie" is a case where several rows share the max version, and _resolve_ties resolves them in Python: it fetchall()s every tied group, then builds one SQL IN (…) literal containing every tied primaryid and scans six child tables with it.

So the tie-break has to move into SQL before the COALESCE lands. Its decisions don't change — most child rows, then most non-null demo fields, then lowest primaryid — which is what keeps the existing tie tests meaningful. That ordering expresses directly as a windowed ROW_NUMBER() over pre-aggregated child counts.

What fixed it

Blank FOLL_SEQ is now version 0, which is what it means, and the tie path moved into SQL first so the extra 592,682 ties had somewhere to land. The 195 unparseable-version rows became version 0 too, rather than being dropped — 29 cases had no other row and were being deleted outright over a typo'd version number.

7. Seven rows with no caseid, sharing one partition fixed

Found within minutes of fixing bug 6, by the orphan tripwire that had just been relabelled — it came back non-zero on the very next preflight, which by its own docstring was supposed to be impossible.

Seven DEMO rows in the entire 24.8M-row archive have a NULL caseid. PARTITION BY caseid puts all seven in a single partition, so the max-caseversion filter kept whichever one happened to have the highest version number and discarded the other six — unrelated reports, years apart, competing as though they were versions of one case.

The survivor then couldn't rejoin DEMO, because dedup_table matches DEMO on the (caseid, primaryid) pair and NULL = NULL is NULL. Its DEMO row was dropped while its child rows sailed through the primaryid-only child filter:

canonical_orphan_rows_reac: 14      ← "structurally always 0"
canonical_orphan_rows_drug:  3
canonical_orphan_rows_rpsr:  3
canonical_orphan_rows_ther:  3
canonical_orphan_rows_indi:  2
canonical_orphan_rows_outc:  2

A row with no caseid has no case identity: it can't be deduplicated against anything and can't be matched against the retraction lists. It and its children are now excluded explicitly, with the primaryids logged.

This one is only visible because bug 6's fix let those rows into the grouping in the first place — while NULL-caseversion rows were being dropped, the NULL-caseid rows were being dropped along with them, for the wrong reason. Two bugs cancelling is not the same as no bug.

8. The 60-case collapse open — needs a ruling

Not a bug; a modeling decision that hasn't been made. 60 primaryids are the winning max-version report of two different caseids at once. _resolve_conflicting_primaryid_rows collapses on primaryid to keep it usable as an identity column for the child-table joins, which drops one case of each pair from canonical.

Either primaryid uniqueness or case completeness has to give. It is logged at WARNING with examples on every load rather than resolved silently, because once the collapse runs the dropped caseids are simply absent and no downstream count can distinguish that from a case that never existed.

WARNING 60 primaryid(s) are the winning version of more than one caseid;
collapsing to keep primaryid unique drops 60 case(s) from canonical.
Examples: primaryid 4522478 -> caseids ['5652629', '5696045'], …

What generalises

FailureThe lesson that isn't specific to DuckDB
1A limit set above the real ceiling doesn't just fail to help — it disables the graceful path underneath it.
2Instrumentation that re-executes the thing it measures is not free. Prefer metadata already written.
3Two buffers on one budget: whenever a producer feeds a buffering writer, land the intermediate.
4When the failing unit is the smallest one, the cause is sequence, not size.
5"Documented as unique" is a claim about intent. Verify uniqueness on the real archive before keying on it.
6Three-valued logic silently deletes. NULL = NULL in a WHERE is a filter you didn't write.
6A check that compares an output to itself validates nothing. Reconcile against the input.
6A column's name in the canonical schema is not its semantics in the source era. FOLL_SEQ really does map to caseversion — and blank still means 0, not unknown.
7A NULL in a PARTITION BY is not a group of one; it is one group of all of them.
7When a check that "can't fail" fails, believe the check. Its docstring is a claim, and this one was wrong twice in an hour.
